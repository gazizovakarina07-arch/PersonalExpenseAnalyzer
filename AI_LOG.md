## 2026-09-09 — проектирование архитектуры v0.2

**Контекст:** после утверждения Product Brief требовалось разделить приложение на модули, определить ответственность классов и выбрать технические решения до написания кода.

**Запрос к ИИ:** предложить архитектуру Personal Expense Analyzer, которая выполняет требования по ООП, композиции, полиморфизму, обработке ошибок и тестированию, но остаётся выполнимой начинающим разработчиком.

**Предложение ИИ:** разделить проект на `domain`, `application`, `infrastructure`, `presentation` и `tests`; использовать интерфейсы для импорта и хранения, полиморфные правила категоризации, целочисленное представление денег и консольный интерфейс. Первоначально ИИ предложил файловое хранение в MVP с последующим переходом на SQLite.

**Как проверено:** архитектура сопоставлена с пользовательским сценарием из `PRODUCT.md`. Было установлено, что транзакции, счета, категории, правила и бюджеты являются связанными данными, а временное файловое хранение потребует последующей миграции.

**Моё решение:** сохранить предложенное разделение на модули и интерфейс `IStorage`, но сразу использовать реализацию `SqliteStorage`. Qt и локальная модель ИИ оставлены расширениями после работающего MVP.

**Фиксация:** версия `v0.2` в истории Git.

## 2026-09-09 — выбор SQLite для хранения данных

**Контекст:** после определения пользовательского сценария требовалось выбрать способ сохранения транзакций, категорий, правил и бюджетов между запусками программы.

**Запрос к ИИ:** сравнить использование SQLite, локальных структурированных текстовых файлов и вариант без сохранения состояния для первой версии проекта.

**Предложение ИИ:** первоначально использовать текстовые файлы через стандартную библиотеку C++, поскольку это уменьшает количество зависимостей и упрощает начало разработки. SQLite предлагалось подключить позднее. Вариант без сохранения был признан несоответствующим пользовательскому сценарию.

**Как проверено:** я сопоставила варианты с предметной моделью. Транзакции связаны со счетами и категориями, правила ссылаются на категории, а бюджеты задаются для категории и месяца. При текстовом хранении пришлось бы самостоятельно разрабатывать формат, проверять его целостность, поддерживать связи между данными и позднее выполнять переход на SQLite.

**Моё решение:** отказаться от временного файлового хранения и использовать SQLite с первой рабочей версии. SQLite работает локально, не требует отдельного сервера, поддерживает связанные таблицы и транзакции. Рабочий файл базы данных не должен добавляться в Git.

**Фиксация:** решение описано в `ADR-003` и вошло в версию `v0.2` в истории Git.

## 2026-09-26 — переход к последовательной разработке v0.3

**Контекст:** после проектирования архитектуры был сразу создан большой черновик первой рабочей версии. В нём одновременно появились система сборки, предметные классы, импорт CSV, категоризация, SQLite-хранилище и тесты. Проект собирался, но такая последовательность не позволяла мне понять назначение каждого файла, работу кода и причины принятых решений.

**Запрос к ИИ:** сохранить опубликованную версию `v0.2`, убрать большой незавершённый черновик из рабочей папки и начать разработку заново небольшими проверяемыми этапами.

**Предложение ИИ:** сохранить все незавершённые изменения командой `git stash push -u`, отдельно удалить автоматически созданные каталоги сборки и тестовую базу, затем проверить состояние Git и вернуться к содержимому тега `v0.2`.

**Как проверено:** команда `git stash list` показала сохранённый черновик `stash@{0}`; `git status --short` не вывела изменений; команда `git describe --tags --exact-match` показала тег `v0.2`. Каталоги `.vs` и `out`, а также тестовая база `data/personal_expenses.db` были удалены как автоматически создаваемые файлы.

**Моё решение:** не продолжать работу с большим готовым черновиком. Каждый следующий файл создавать отдельно, предварительно разбирать его назначение и код, после чего выполнять небольшую проверку и записывать результат в журнал.

**Фиксация:** черновик сохранён локально в `stash@{0}`; рабочая папка возвращена к состоянию `v0.2`.

## 2026-09-26 — создание минимальной программы и настройка CMake

**Контекст:** в версии `v0.2` находилась только проектная документация. Для начала реализации требовалось создать минимальную программу и отдельно проверить весь путь от исходного кода до запуска исполняемого файла.

**Запрос к ИИ:** последовательно объяснить создание первого исходного файла, назначение каждой строки программы и настройку системы сборки CMake.

**Предложение ИИ:** создать файл `src/presentation/main.cpp` с функцией `main`, которая выводит название приложения, а также корневой файл `CMakeLists.txt`, создающий исполняемую цель `PersonalExpenseAnalyzer`. Первоначально в настройке был указан стандарт C++20.

**Как проверено:** наличие `CMakeLists.txt` проверено командой `Get-Item`; доступность CMake — командой `cmake --version`. Конфигурация выполнена командой `cmake -S . -B out/build -A x64`, сборка — командой `cmake --build out/build --config Debug`. Созданный файл `out/build/Debug/PersonalExpenseAnalyzer.exe` был запущен и вывел строку `Personal Expense Analyzer`.

**Моё решение:** использовать минимальную программу как первую проверяемую основу проекта. При сравнении настройки с предыдущей записью журнала обнаружено расхождение: CMake использовал C++20, тогда как для проекта был запланирован C++17. Поскольку возможностей C++17 достаточно, я изменила `CMAKE_CXX_STANDARD` с `20` на `17`, повторно выполнила конфигурацию, сборку и запуск.

**Фиксация:** отдельный коммит этапа разработки версии `v0.3`.
