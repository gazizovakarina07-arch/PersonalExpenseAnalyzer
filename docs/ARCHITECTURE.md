# Архитектура Personal Expense Analyzer

Версия документа: `v0.2`

## 1. Цель архитектуры

Приложение должно импортировать операции из CSV, проверять данные, распределять операции по категориям, контролировать бюджеты и формировать месячный отчёт. Основная бизнес-логика не должна зависеть от консольного интерфейса, формата CSV и SQL-запросов.

## 2. Модули

| Модуль | Ответственность |
|---|---|
| `domain` | Финансовые сущности и правила предметной области |
| `application` | Выполнение пользовательских сценариев и координация объектов |
| `infrastructure` | Чтение CSV и сохранение данных в SQLite |
| `presentation` | Консольное меню, ввод команд и показ результатов |
| `tests` | Проверка бизнес-правил независимо от интерфейса |

Направление зависимостей:

```text
presentation ──────> application ──────> domain
                           ↑                 ↑
                           └── infrastructure
```

Интерфейсы инфраструктуры объявляются на уровне `application`, а их реализации находятся в `infrastructure`. Модуль `domain` не знает о консоли, CSV, SQLite, CMake и будущей модели ИИ.

## 3. Основные классы

### Domain

| Класс | Ответственность |
|---|---|
| `Transaction` | Хранит дату, описание, сумму, счёт и категорию одной операции |
| `Account` | Представляет пользовательский счёт и связанные с ним операции |
| `Category` | Описывает категорию дохода или расхода |
| `Budget` | Хранит лимит категории за месяц и определяет факт превышения |
| `ICategorizationRule` | Задаёт общий интерфейс правила категоризации |
| `KeywordCategorizationRule` | Назначает категорию при обнаружении ключевого слова в описании |
| `ExactDescriptionRule` | Назначает категорию при точном совпадении описания |
| `MonthlyReport` | Хранит итоги месяца, суммы по категориям и предупреждения |

Суммы хранятся в `int64_t` как целое количество минимальных денежных единиц, например копеек. Это исключает ошибки округления чисел с плавающей точкой.

### Application

| Класс или интерфейс | Ответственность |
|---|---|
| `ExpenseApplication` | Координирует импорт, категоризацию, бюджеты, отчёты и сохранение |
| `IStatementImporter` | Задаёт общий контракт импорта банковской выписки |
| `IStorage` | Задаёт операции сохранения и загрузки состояния приложения |
| `TransactionCategorizer` | Последовательно применяет правила и возвращает категорию либо статус «Не определено» |
| `ReportGenerator` | Рассчитывает месячные итоги и выявляет необычно крупные расходы |

`ExpenseApplication` не содержит формул отчёта, разбора CSV и SQL-запросов. Он вызывает соответствующие объекты в нужной последовательности.

### Infrastructure

| Класс | Ответственность |
|---|---|
| `CsvStatementImporter` | Реализует `IStatementImporter` и читает один документированный формат CSV |
| `SqliteStorage` | Реализует `IStorage` и сохраняет счета, транзакции, категории, правила и бюджеты в SQLite |

### Presentation

| Класс | Ответственность |
|---|---|
| `ConsoleUI` | Показывает меню, принимает ввод, сообщает об ошибках и выводит отчёт |

## 4. Композиция и полиморфизм

`ExpenseApplication` получает реализации `IStatementImporter` и `IStorage` извне. Благодаря этому бизнес-логика не зависит от конкретного формата выписки и SQL-кода.

`TransactionCategorizer` содержит набор объектов `ICategorizationRule` и последовательно применяет их к транзакции. В MVP используются два содержательных правила: по ключевому слову и по точному описанию. Новое правило можно добавить отдельным классом без изменения существующих правил.

## 5. Основной сквозной сценарий

```text
ConsoleUI
   ↓ команда импорта
ExpenseApplication
   ↓
CsvStatementImporter
   ↓ список проверенных Transaction
TransactionCategorizer
   ↓ категоризированные операции
SqliteStorage
   ↓ сохранённое состояние
ReportGenerator использует Transaction, Category и Budget
   ↓ MonthlyReport
ConsoleUI показывает результат
```

Первый вертикальный прототип `v0.3` реализует сокращённую цепочку: импорт демонстрационного CSV → проверка строк → создание и категоризация транзакций → сохранение в SQLite → вывод суммы по категориям.

## 6. Ошибки и проверка входных данных

- отсутствующий файл приводит к понятному сообщению, а не к аварийному завершению;
- заголовок CSV и количество полей проверяются до создания транзакций;
- неверная дата или сумма отклоняются с указанием номера строки;
- пустое описание операции считается ошибкой;
- при ошибке импорта изменения не сохраняются частично;
- ошибки SQLite обрабатываются в `SqliteStorage` и передаются приложению в понятном виде;
- ошибки инфраструктуры перехватываются на границе приложения и преобразуются в сообщения для пользователя.

## 7. Хранение данных

Для MVP используется локальная база SQLite. В ней хранятся счета, транзакции, категории, правила категоризации и месячные бюджеты. CSV используется как входной формат импорта, а не как основное хранилище приложения.

Интерфейс `IStorage` отделяет бизнес-логику от SQL-запросов. Конкретную работу с базой выполняет `SqliteStorage`. Операции импорта, состоящие из нескольких записей, выполняются в транзакции SQLite: при ошибке вся операция отменяется.

Предварительная схема базы:

| Таблица | Основные данные |
|---|---|
| `accounts` | Идентификатор и название счёта |
| `categories` | Идентификатор, название и тип «доход/расход» |
| `transactions` | Счёт, дата, описание, сумма в копейках и необязательная категория |
| `categorization_rules` | Тип правила, шаблон, категория и приоритет |
| `budgets` | Категория, месяц и лимит в копейках |

`transactions` ссылается на `accounts` и при наличии категории — на `categories`. Правила и бюджеты также ссылаются на категории. Точная SQL-схема будет зафиксирована вместе с первой реализацией хранилища.

Рабочая база пользователя и настоящие банковские выписки не добавляются в Git. Для демонстрации используется вымышленный CSV, а для тестов — отдельная временная база SQLite.

## 8. План тестирования

Автоматические тесты проверяют:

- создание корректной транзакции и отклонение неверной суммы или даты;
- срабатывание каждого типа правила категоризации;
- сохранение статуса «Не определено», если правило не найдено;
- расчёт суммы расходов по категории;
- превышение и точное достижение бюджета;
- формирование отчёта для пустого месяца;
- обработку повреждённой строки CSV;
- сохранение и повторную загрузку данных через SQLite;
- отмену всех изменений при ошибке в процессе импорта.

Тесты обращаются к бизнес-логике напрямую, без запуска `ConsoleUI`.

## 10. Расширения после MVP

- графический интерфейс Qt как новая реализация слоя `presentation`;
- импорт выписок других форматов через новые реализации `IStatementImporter`;
- локальная модель ИИ для предложения категории только тем операциям, которые не распознаны обычными правилами.
